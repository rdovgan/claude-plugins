# Decisions and deviations from the requirements

Notes for the tech lead. Current Claude Code documentation takes priority over the requirements.

| ID | Topic | Decision / reason | Status |
| --- | --- | --- | --- |
| D-01 | Names | Marketplace `team-plugins`, plugin `java-developer`, repository `claude-plugins` are the names proposed in the requirements; change them if the owner provides others | Open |
| D-02 | Rule syntax | `templates/settings.json` uses `Bash(mvn test *)` (space before `*`) and the `sandbox.filesystem.denyRead` / `sandbox.network.allowedDomains` blocks. Verify against current settings docs before release; `claude plugin validate` does not check the template | To verify |
| D-03 | `session-summary` | Ported from `~/.claude/commands/session-summary.md` together with `scripts/save_session.sh`. Logic unchanged; only machine-specific paths were removed: the hardcoded local vault path became `$JAVA_TEAM_VAULT` (default `~/Claude Vault`; `VAULT` still overrides), and the script path became `${CLAUDE_PLUGIN_ROOT}`. The skill writes to each developer's Obsidian vault, so everyone must set `JAVA_TEAM_VAULT` | Ported, agree with owner |
| D-04 | Jira MCP | Uses the remote server `https://mcp.atlassian.com/v1/mcp` (`type: http`, OAuth). It has no tool to download attachments: `getJiraIssue` returns `attachment/content/<id>` URLs on `api.atlassian.com` that need the OAuth token the agent does not have. Attachments are downloaded by `scripts/jira-attachments.sh` with a personal API token (`JAVA_TEAM_JIRA_URL`, `JAVA_TEAM_JIRA_EMAIL`, `JAVA_TEAM_JIRA_TOKEN`), GET only, the token passed to curl on stdin. A second community MCP server with a download tool was rejected: one more runtime and config per developer | Implemented |
| D-05 | DB MCP | DBMS is MySQL. `scripts/db-mcp.sh` runs `@benborla29/mcp-server-mysql@2.0.9` (version pinned; writes disabled via `ALLOW_*_OPERATION=false`; the real read-only guarantee is the DB user's grants). Variables: `JAVA_TEAM_DB_URL` (`mysql://host:port/db`, no credentials), `JAVA_TEAM_DB_USER`, `JAVA_TEAM_DB_PASSWORD`. The server does not start without them. Verify the package choice and variable names against its docs | To verify |
| D-06 | Sandbox network | Hosts are placeholders in `templates/settings.json` (`<NEXUS_HOST>`, `<GIT_HOST>`, `<JIRA_HOST>`); `permissions-setup` asks for them and removes the ones it cannot fill. `mcp.atlassian.com` is fixed | Accepted |
| D-07 | Marketplace git URL | Default `git@github.com:rdovgan/claude-plugins.git`; `project-init` asks to confirm it (a fork or mirror needs its own URL; `install.sh` accepts `MARKETPLACE_URL`) | Accepted |
| D-08 | `verify.sh` and `stop_hook_active` | Requirement: do not block twice. Implemented: with `stop_hook_active=true` tests run again but a failure only warns instead of blocking, so no loop is possible and the fix is still verified. The `session-summary` reminder is sent once per session via a flag | Implemented |
| D-09 | "Changed in session" | `verify.sh` takes `.java` files from `git diff` against the base (`main`/`master`) plus new files, filtered by mtime newer than the marker created by `session-start.sh` | Implemented |
| D-10 | `test-writer` restriction | Writing only to `src/test/**` cannot be expressed in `tools`; it is enforced by `guard-files.sh` via the `agent_type` field of the hook input JSON. Verify that Claude Code passes this field for subagents | To verify |
| D-11 | `tools` with patterns | `java-reviewer` uses `Bash(git diff:*)` etc. in `tools`. Verify that plugin subagents accept such patterns; otherwise use plain `Bash` restricted in the prompt | To verify |
| D-12 | Language | All plugin content (docs, skills, agents, hook messages, templates) is in English | Accepted |
| D-13 | Team workflow | `reference/team-workflow.md` is a template of the usual rules (branches, commits, PRs, DoD); a team replaces it with its own. `guard-bash.sh` enforces protected branches (`main`, `master`, plus `JAVA_TEAM_PROTECTED_BRANCHES`) and no attribution | Implemented |
| D-14 | Code style | Not hardcoded: `project-init` fills `{{STYLE_SECTION}}` of the `CLAUDE.md` template from the project's own formatter config or from the user. `format.sh` does not enforce it | Implemented |
| D-15 | Migrations | The `ask` rule covers `**/db/changelog/**` and `project-init`/`permissions-setup` extend it to `changelog/` and `db/migration/` directories found in the project | Accepted |
| D-16 | Guard on `git commit` | Commits on protected branches are blocked, which also applies when the plugin is enabled in this plugin repository itself; work on a branch | Accepted |
| D-17 | Multi-repo access | The workspace folder holds unrelated files (tokens, exports), so it is never added as a whole. `project-init` lists the repositories named in the module map as `permissions.additionalDirectories` (`../<repo>`). Verify that relative paths resolve against the project root and that a missing directory is harmless. `deny` rules and hooks apply to added directories; their own `.claude/settings.json` and `CLAUDE.md` are not loaded | To verify |
| D-18 | Multi-repo guards | `guard-bash.sh` resolves the target repo per command segment (hook `cwd`, `cd`, `git -C`) and applies the branch rules (protected-branch commit/push) to it. Not handled: `--git-dir`/`--work-tree`, `cd` inside `$(...)` or via variables | Implemented |
| D-19 | `java-analyst` as a separate plugin | Chosen over a mode of `java-developer`: it is installed on its own, and it must be self-contained, so `task-research`/`task-interview`/`code-explorer`, `scan-modules.sh` and `modules.md` are copied and adapted, not shared. Cost: copied files drift; sync them by hand when `java-developer` changes (`reference/modules.md` especially) | Accepted |
| D-20 | Read-only enforcement | By hooks, always on (no per-session marker): `guard-files.sh` allows writes only under `<project>/.claude/analysis/` (symlinks resolved), `guard-bash.sh` is an allowlist (no redirects, `$()`, builds, git writes), `guard-mcp.sh` allows only get/search/list/read/fetch/find tools, so IDE `apply_patch`, mail and Jira edits are refused. Fails closed without `jq`. Escape hatch: `JAVA_ANALYST_OFF=1` | Implemented |
| D-21 | Known limits of the guard | Secret protection is by file name, as in `java-developer`; a recursive `grep -r` can still read a `.env` in the tree (ship the `deny` rules from `java-developer`'s `templates/settings.json` in the project). Interpreters (`python`, `node`) are not on the allowlist, so analysis cannot run scripts | Accepted |
| D-22 | Output location | `.claude/analysis/<KEY>/` in the project, 7 documents. Git exclusion goes to `.git/info/exclude` (done by the SessionStart script) so the tracked `.gitignore` is never edited. No Jira/Confluence publishing; Jira is read only | Implemented |
| D-23 | Jira MCP in `java-analyst` | Ships the same remote server as `java-developer` for reading tickets; write tools are blocked by `guard-mcp.sh`. Both plugins in one project would register two `jira` servers and two sets of hooks, so use one of them | To verify |
| D-24 | Completion check | `verify-analysis.sh` (Stop) blocks once if an analysis touched in the session lacks a document, keeps `{{placeholders}}`, or `03-flows.md` has no mermaid block; with `stop_hook_active` it only warns | Implemented |
| D-25 | Plugin rename | `java-team` became `java-developer` (0.8.0): the name did not say what the plugin does, next to `java-analyst`. Not renamed, to avoid breaking existing setups: the `java-team:generated` markers in `CLAUDE.md` files, the `JAVA_TEAM_*` variables, the marketplace name `team-plugins`. Old installs must be reinstalled; `project-init` update mode migrates `enabledPlugins`. D-01 and older entries keep describing the original names | Implemented |
| D-26 | Both plugins in one project | Unsupported. With both enabled a bare ticket key triggers both `UserPromptSubmit` hooks and both research skills (the model picks by description, not deterministically), and the always-on guards of `java-analyst` block specs, code, tests and commits of `java-developer`. Not made to coexist (a marker-based opt-in guard was considered and rejected: a developer who forgets `/analyze` would be unprotected). Each session-start hook warns once when the other plugin is enabled | Implemented |
| D-27 | Shared DB variables | `java-analyst` reuses `JAVA_TEAM_DB_URL/USER/PASSWORD` (the names are kept after the rename, D-25) and carries its own copy of `db-mcp.sh` (D-19: no cross-plugin dependency; keep the copies in sync). Its guard adds a SELECT-only filter on top of the read-only DB user (D-05). The filter reads the statement from `tool_input.sql` or `tool_input.query`; verify the real parameter name of `@benborla29/mcp-server-mysql`, a mismatch makes every query refused (fails closed). `JAVA_TEAM_VAULT` is not used: `java-analyst` has no `session-summary` | To verify |
| D-28 | Write policy of `java-analyst` | Relaxes D-20: the first version allowed writes only under `.claude/analysis/`, which also blocked `CLAUDE.md` and settings. Now: inside the project, documentation extensions, `CLAUDE.md`, `.gitignore`, `.mcp.json` and `.claude/**`; everything else, including build files and app configs, is refused. Accepted trade-off: the agent can edit `.claude/settings.json`, so it could in theory disable the plugin on a user's request; the guard protects against accidental code changes, not against a determined user (`JAVA_ANALYST_OFF=1` exists anyway) | Implemented |
| D-29 | Bash allowlist | Extended for common read-only tools after a report that a piped exploration command was refused. The refusal message names the command; if a legitimate read-only command is still refused, add it to `guard-bash.sh` with its dangerous options blocked | Implemented |
| D-30 | `qa-docs` as a third plugin | Separate from `java-analyst`: different users (QA), place (shared server, session in the workspace root), output (shared domain documents, Confluence export) and write policy. Copied and adapted, not shared (D-19): `guard-bash.sh`, `mark-onboarded.sh`, the pom part of `scan-modules.sh`, the path helpers of `lib.sh`. Keep the Bash allowlist in sync with `java-analyst` | Implemented |
| D-31 | Boundary on the server | File permissions are the real read-only guarantee (sources not writable for group `qa`); hooks keep the agent within its purpose and explain refusals. No off switch, unlike `JAVA_ANALYST_OFF`: on a shared server a user must not be able to drop the guards | Implemented |
| D-32 | Confluence writes | Allowed only for the plugin's own Atlassian server: create in `QA_DOCS_CONFLUENCE_SPACE` under `QA_DOCS_CONFLUENCE_PARENT` (or under a page qa-docs exported), update only page ids found in `domains/*/meta.json`. The agent writes `meta.json` itself, so the id list is a guard against mistakes, not against intent; the human gate is the `ask` rule for both tools in `templates/settings.json` (and managed settings). Diagrams are exported as mermaid code blocks: the Confluence site has no mermaid or draw.io app, and the MCP server cannot upload attachments for PNGs (PNGs are rendered and kept on the server, D-38). Since 0.3.0 also: children of exported pages (`confluence.pages`), and one footer comment on the old page of a mirror document (`source.pageId`, D-39) | Implemented |
| D-33 | Shared results, personal sessions | Results live in `<workspace>/qa-docs/` (group-writable, setgid, default ACL). Concurrent edits are prevented by hook-managed locks in `qa-docs/.locks/`, one per domain and one for both maps; stale after `QA_DOCS_LOCK_MINUTES` (default 120). The maps are `qa-docs/modules.md` and `qa-docs/domains.md`: inside the workspace as agreed, next to the results so every session can update them | Implemented |
| D-34 | Freshness | Cron mirrors `master`/`main` nightly (`branches.conf` for exceptions); documents record the commit of every repository they rely on, so `/qa-docs:refresh` diffs from there. A session snapshots commits at start; the Stop hook warns when cron moved them mid-session | Implemented |
| D-35 | Sensitive file patterns | Built-in names extended for PHP/JS (`auth.json`, `wp-config.php`, `parameters.yml`, `.npmrc`, ...) and `gitleaks-report*`; `credentials*` and `*secret*` do not apply to source files (`CredentialsService.java`). Repository-specific ones (for example `application.properties` with passwords) go to `.qa-docs/sensitive.txt`; the admin should run a scanner once and list what it finds. `Grep` over a folder relies on ripgrep's `.gitignore` handling and the deny/sandbox rules for files inside it | To verify |
| D-36 | Usage limits on a large workspace | A full run on 30 repositories used two 5-hour limits: agents inherited the session model, research had no bound, and the same code was read three times (agent, main session, fact-checker). Now agents run on Sonnet, research is bounded by `QA_DOCS_MAX_SUBFLOWS` and pauses for the user, the main session only spot-checks, verification uses at most 3 agents, questions go to `/qa-docs:ask`, and `<workspace>/.ignore` keeps build output and dependencies out of searches. Depth that does not fit the budget is recorded as "not traced yet" and continued in a later run. Whether Glob honours `.ignore` like Grep (ripgrep) does is not verified | Implemented |
| D-37 | Document as a page set | QA feedback on 0.2: one `domain.md` with every section was too long to read. Now `doc/` holds a short overview (`README.md`), one page per process (the research sub-flows) and reference pages; a rule is stated once in `rules.md` and linked. The research files (`00`-`03`, `work/`) stay next to `doc/` as the trail. Exported as a Confluence page tree with the same shape. Old documents move with `/qa-docs:rewrite` (no new research) | Implemented |
| D-38 | Diagrams as PNG on the server | No mermaid app in Confluence and no attachment upload in the MCP server; public renderers (mermaid.ink, kroki.io) are not used because they would send internal business logic outside. `render-diagrams.sh` renders each block with mermaid-cli and a shared system Chromium (`QA_DOCS_CHROME`; puppeteer's own download is per user) into `doc/diagrams/<name>.png` next to `<name>.mmd`; the markdown keeps both the picture line and the mermaid block, and Confluence gets the code plus the PNG path. Uploading the PNGs through the Confluence REST API with a token would put them on the pages; not done for now (needs a token per user and a second write path). Rendering inside the Claude Code sandbox is not verified on the server | To verify |
| D-39 | Updating an old Confluence page | `/qa-docs:update-page` writes a new page in the old page's structure (layout `mirror`) and a "what changed" child, under the qa-docs parent rather than under the old page: the guard keeps all writes inside the qa-docs tree, and the old page's space may not be writable for QA. Discoverability comes from one footer comment with the link on the old page, agreed with QA; the old page itself is never edited | Implemented |
| D-40 | Plan review by a stronger model | `spec-reviewer` (Opus, Read/Grep/Glob) checks the spec before it is shown to the user. Only for complex tasks and standard ones that change a contract, a table or several repositories, one pass, and it gets the spec and the quoted requirements rather than the session history, to stay within usage limits (see D-36). Whether it catches more than `java-reviewer` alone is not measured yet: compare on a few closed tickets where the plan missed something | Implemented |
